# Kivact 技術設計レビュー用テンプレート

参照戦略: [製品戦略 v2](20261009_strategy.md)

以下をレビュー依頼として使用する。対象設計書のパスを埋め、必要なら対象commit・検証環境を追加する。

---

`docs/for-kivact-developer/strategy/20261009_strategy.md`を参照し、次の技術設計が、対象ユーザーに選ばれ、完成・保守できるフレームワークにつながるかレビューしてください。

対象設計書: `<パス>`

対象commit / version: `<指定または未固定>`

必須事項:

1. 事実、推論、提案、未検証を分ける。対象設計書を読んだだけで実装済み・試験済みとしない。
2. どの利用者のどの仕事が改善するかを最初に書く。根拠になる実アプリの要求（戦略 3 章）を示す。
3. 層が戦略 4 章の所有範囲に合っているかを判定する。アプリが公開 API だけで作れるものを中核に入れていないか、作れないものをアプリに残していないかを見る。
4. 公開 API を、Rust 未経験の React・SolidJS 開発者を基準に評価する。同じことに二つの経路がないかを確かめる。
5. G-01〜G-07 の違反は、機能の魅力で相殺しない。構造的な欠陥と、限定試作で確かめられる不確実性を区別する。
6. 性能は局所の更新だけでなく、layout、paint、graph、memory、ビルド時間を必要な範囲で評価する。
7. 試験は実 window 上の E2E を最優先する。window を開かない試験で代える場合は、その理由を書く。
8. 改善案は目的を満たす最小の変更を優先し、実装・検証・保守の負担と、P0・P1 との優先関係を示す。

出力形式:

- **結論:** 採用 / 条件付き試作 / 保留 / 却下・再設計。対象範囲と確信度を明示する。
- **対象利用者の利益:** 現状の課題、改善後の仕事、成功を判断する観測。
- **重要な指摘:** 重大度順。各項目に設計書の場所、根拠、利用者への影響、対応する G・P・N、最小の修正案を書く。
- **問いの判定表:** 戦略 10 章の問い 1〜8 を、適合 / 不適合 / 未検証 / 非該当と根拠で判定する。
- **最小検証方法:** 仮説、検証範囲、測定方法、合否条件、失敗時の撤回方法。
- **残る制約:** 現時点で保証できない OS・操作・互換性。戦略の変更が必要なら、その理由を明示する。

指摘がない場合も、確認できた範囲と未検証の範囲を書いてください。根拠のない「将来の拡張性」や「圧倒的性能」を承認の根拠にしないでください。
