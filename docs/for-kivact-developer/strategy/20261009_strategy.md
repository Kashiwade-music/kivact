# Kivact 製品戦略 v2

版: 2.5（2026-10-31）
前版: [v1.7 の固定した履歴](https://github.com/Kashiwade-music/kivact/blob/2d8e32abca180a35e9ccd82d59b452fd7b04e441/docs/for-kivact-developer/strategy/archive/20260924_strategy.md)（2026-09-25）。v1 の ID との対応は付録にある。

本書は、何を Kivact に入れ、何を入れないかを決めるための戦略である。内部の構造と API の詳細は [設計](../design.md) に置く。本書は約 200 行に保ち、増やす場合は同じ量を削る。

## 1. 製品の定義

> **Kivact は、データ量の多い業務・開発ツールとクリエイティブ編集ツールを、React・SolidJS の知識で組み立て、Rust のドメインロジックと同じコードベースで出荷できる、変更に強いクロスプラットフォーム GUI フレームワークである。**

これは目標であり、現在の完成機能を示す広告ではない。特徴は一機能ではなく次の組合せにある。

| 特徴 | 利用者に届ける価値 |
|---|---|
| React・SolidJS からの移行経路 | コンポーネント、状態、効果の知識をそのまま使い、Rust を段階的に学べる |
| 実用画面を完成させる標準経路 | 一覧、入力、非同期処理、保存、配布まで、部品と OS サービスを迷わず選べる |
| 更新理由を追える仕組み | 状態変更から依存、レイアウト、描画までの原因を調べられる |
| OS と整合する操作品質 | IME、フォーカス、キーボード操作を、部品の外観と独立に守る |
| アクセシビリティ対応 | どの部品も役割・名前・状態を OS の支援技術へ出し、スクリーンリーダーとキーボードだけで操作できる。外観を変えても、独自部品を作っても、この意味を失わない |
| 実画面の E2E テスト | `cargo test` から実際の window を開き、利用者と同じ入力で操作し、役割と名前で要素を探して確かめられる。レイアウト崩れも機械的に検知できる |
| 多言語対応 | CJK、結合文字、双方向テキスト、IME の入力を扱う。地域ごとの日付・数値・週の始まりは実装予定。部品の既定の文言はすべて差し替えられる |
| 自由な外観と描画 | テーマ、Canvas、新しい基本部品で、操作と意味を壊さず製品固有の表現を作れる |

「最速」「ゼロコスト」「React のコードをそのまま移せる」「完全なネイティブ体験」は、定義と証拠なしに使わない。

## 2. 対象

| 対象 | 位置付け | 理由・再検討条件 |
|---|---|---|
| Rust 資産を持つデスクトップ業務・開発ツール | 主対象 | 同一言語の利益と実用 UI の課題を同時に検証できる |
| タイムライン・キャンバス・インスペクターを持つクリエイティブ編集ツール | 主対象 | 共通する編集操作を公開 API で成立させる。分野固有のエンジンはアプリが持つ |
| React・SolidJS 開発者（Rust 経験を問わない） | 主対象 | 既存の UI 知識を移せることが採用の入口になる。Rust の所有権・型・非同期で止まる箇所を教材と API で減らす |
| DAW プラグインの editor（CLAP・VST3、Windows と Linux X11） | 主対象 | 主対象のクリエイティブ編集ツールの一形態。所有者が要求を確認（2026-10-31）。Kivact は window と UI、規格や枠組みとの glue はアプリ（wrapper） |
| モバイル | 設計・実機検証の対象。正式対応は保守能力で判断 | ライフサイクル、タッチ、ソフトウェアキーボード、状態復元を設計から外さない |
| 企業の独自プラットフォーム | 長期の設計協力先 | SDK、実機、契約、保守主体がそろったときだけ正式対応を判断 |
| Web 中心の SaaS、ゲーム内 UI、大規模 Qt 移植、認証が必要な組込み | 対象外 | Web 資産・即時モード・既存資産の利益を覆す根拠が必要 |

API の使いやすさは、Rust 未経験の React・SolidJS 開発者を基準に判断する。JSX、Hooks の規則、DOM 互換は約束しないが、対応表と差分の説明を必ず用意する。

## 3. 取り込みの規則

1. **実アプリの要求を根拠にする。** Kivact で作る実アプリ（作者の dogfooding を含む）と外部利用者が、公開 API で実現できなかった操作を取り込みの根拠とする。要求のない部品や option は先行して作らない。
2. **汎用の形に作り直して入れる。** アプリの画面や語彙に寄った契約は、別の用途でも説明できる形に作り直す。アプリのコードをそのまま移さない。
3. **層を 4 章で決める。** 中核に入れるか、公式 kit に入れるか、アプリに残すかは所有範囲の表に従う。迷ったら「アプリが公開 API だけで作れるか」を問い、作れないものを中核の拡張口として優先する。
4. **経路を一つにする。** 同じことを二つの方法で書ける契約（定数と Binding の二つの mode、通知の重複、関数名の組合せの増殖）は一つにまとめる。
5. **見送りは記録する。** 見送ったものは、アプリでの代替手段と再検討の条件を残す。記録先は [台帳](ledger.md)。
6. **2 つ以上の公式 kit が同じ意味の部品を持つなら、中核の標準部品か interaction にする。** kit は theme と分野固有の部品だけを持つ。

## 4. 所有範囲

| 領域 | 持つ層 | 内容と境界 |
|---|---|---|
| 状態、効果、非同期、時間 | 中核 | signal、memo、effect、task。長い処理を UI スレッドに流す API にしない |
| 入力、focus、hover、IME、キー配送 | 中核 | アプリが作れない部分なので、部品が必要とする口は中核が持つ |
| 部品の振る舞いと semantics | 中核 | button、選択、menu と右クリックメニュー、dialog、popover、tooltip、tabs、splitter、list・table・tree のキー操作、通知領域。見た目を持たない層として、どの kit も同じ振る舞いを使う |
| 編集の取消し | 中核 | drag・キー1回・支援技術の操作1回の始まり・確定・取消しを `EditPhase` で統一する。値を書き換える部品は `on_edit` を出し、取消し時に編集前の値へ戻す。undo の履歴はアプリが持つ |
| 標準部品 | 中核（少数） | button、checkbox、input、select、dialog、menu など、kit なしで最初の実用画面（一覧・表・入力と検証・通知・非同期の状態）を作れる数。見た目は theme の token で決まる |
| 公式 kit | kit | theme（標準部品の見た目の差し替え）と、分野固有の部品（calendar、timeline、dock、outliner、HUD など）。公開 API の `kivact` だけに依存する。選択・キー操作・右クリックメニュー・drag・取消しは `interaction` と `ui` で組む。不足する口は中核へ足し、kit で複製しない |
| 特定アプリの画面と語彙 | アプリ | 分野固有の icon、色の役割、画面構成。kit は Path やテーマの token を渡せる拡張口を用意する |
| アクセシビリティ | 中核 | 役割・名前・状態・操作を AccessKit 経由で OS へ出す。振る舞いの層と標準部品が既定で正しい意味を持ち、独自部品と Canvas の中の操作対象にも同じ口を開く |
| 多言語対応 | 中核とアプリ | 中核は文字の shaping・双方向テキスト・IME、App の locale を持つ。地域ごとの書式（日付、数値、週の始まり）は中核の担当として予定する。部品は既定の文言を持ってよいが、すべて差し替えられるようにする。翻訳の資源と言語の切替はアプリが持つ |
| 2D 描画 | 中核 | style、局所 draw layer、Canvas が同じ描画語彙を持つ。HTML Canvas と Path2D に対応させる |
| アプリが描いた絵の表示 | 中核とアプリ | 3D viewport・合成プレビュー・scope はアプリの GPU・CPU renderer が描く。中核は絵の表示・DPI・サイズ変更・再描画、worker からの frame の受渡し、拡大・pan・座標変換・pointer capture・重ね描き・支援技術の region を持つ。timeline・graph・node editor・color wheel の構造化データは kit が描く。kit はアプリのエンジンの出力を模倣しない |
| 画像の書き出し | 中核 | window なしの RGBA8 描画（OffscreenCanvas に相当）。HDR や浮動小数点の出力はアプリが持つ |
| テキスト編集の拡張口 | 中核（段階的に） | 行単位の配置結果、独自部品の IME セッション、テキストのアクセシビリティ。到達目標は「`text_field` を公開 API だけで作り直せること」で、コードエディタを作れる水準とする |
| アニメーション | 中核 | 目標値への補間と、利用者の毎フレーム計算の二種類。任意の正の目標 fps を指定でき、60 fps の上限を置かない。作品の時間（タイムライン、再生位置、シーク）はアプリが持つ |
| window の起動設定と OS サービス | 中核 | サイズ、最小サイズ、clipboard、ファイル選択、open・reveal。他のプログラムの window への埋め込み（`App::embed`）を含む。プラグインの規格や枠組みとの glue はアプリ。位置と display は、移植可能な不透明な値として扱える形ができるまで入れない |
| 音声 | アプリ | 再生、取得、処理、ASIO などのデバイス管理はアプリが持つ。通知音のような単純な再生は、UI の lifecycle と統合できる形があれば中核で再検討する |
| 試験と診断 | 中核 | 実 window 上の `kivact::test`（E2E）を最優先する。window を開かない試験は、描画結果の検証など E2E で代えにくいものに限って許す。レイアウト崩れ（文字のはみ出し、意図しない折返し、縦位置のずれ）を機械的に検知する検査を持つ |
| 移植の境界 | 中核 | 通常の API にバックエンドの型（winit、wgpu、Vello など）を出さない。接続層の SPI は実験段階とし、二つ目の実装で検証する |

## 5. 妥協しない条件

以下は他の機能の魅力で相殺しない。実験段階でも解決の道筋を示し、正式対応を宣言するときは実証を求める。番号は v1 から変えない。

- **G-01 安全性・ライフサイクル:** 安全な API から未定義動作を起こさない。破棄したコンポーネントへのコールバック、タスク、購読を残さない。アプリ状態と描画サーフェスを分け、休止・復帰・再生成を安全にする。
- **G-02 状態:** バッチ、再入、効果、派生値、条件分岐、識別の意味を定義し、更新漏れや循環を注意書きで隠さない。
- **G-03 入力・意味:** IME の変換中の文字を壊さない。タッチ、フォーカス、選択、キーボード、アクセシビリティを仮想化や描画と整合させる。CJK、結合文字、双方向テキストの対応範囲を示す。
- **G-04 応答・資源:** 長い処理を UI スレッドへ自然に流す API にしない。アンマウント後の資源と待機中の仕事量を測る。
- **G-05 診断:** エラー、パニック、更新理由、OS やバックエンドの制約を調査可能にする。不正な値を黙って無視しない。
- **G-06 契約・移行:** API 変更の影響と代替を説明し、安定宣言後に内部都合で壊し続けない。
- **G-07 表現・意味:** スタイルやアニメーションによって、ヒットテスト、フォーカス、選択、セマンティクスの領域、テスト用識別子を描画と矛盾させない。

## 6. 設計原則

| ID | 原則 | 判断に使う証拠 |
|---|---|---|
| P-01 | 具体的な利用者の仕事から始める | 改善する画面と操作、現在の障害（3 章の実アプリ要求） |
| P-02 | 公開 API を少ない概念で説明する | React・SolidJS との対応、初級例、誤用時の診断 |
| P-03 | 状態とライフサイクルを予測可能にし、観測できるようにする | 分岐、key、並べ替え、削除、更新理由 |
| P-04 | ネイティブ品質は OS 上の実際の操作で評価する | IME、フォーカス、キーボード、アクセシビリティ、DPI の実機結果 |
| P-05 | 最適化は全体の費用で判断する | グラフ、レイアウト、描画、メモリ、ビルド時間 |
| P-06 | 外観と操作・意味を分ける | 同じ振る舞いと semantics の上の複数テーマ、Canvas、新しい基本部品 |
| P-07 | 公式部品と外部部品は同じ公開 API で作る | 公開 API だけの kit、外部コンポーネント、中核のフォーク不要 |
| P-08 | 文書、診断、試験を機能に含める | rustdoc、how-to、E2E、レイアウト検査 |
| P-09 | 約束を現在の能力以上に広げない | 対応表、保守者、実機検証。未対応は Unsupported として示す |
| P-10 | 移植性はバックエンド非依存の契約と狭い SPI で確保する | バックエンド型の非漏洩、模擬実行環境、第二の実装 |

## 7. 非目標

| ID | 非目標 | 再検討の条件 |
|---|---|---|
| N-01 | 全用途・全 OS での同等品質、Web を含む無制限の拡大 | 利用者の課題と、継続的な実機検証・保守の能力 |
| N-02 | React、DOM、CSS の互換実装 | 中心市場を変える需要。CSS 風の型付き style は除外しない |
| N-03 | GPU レンダラー、テキスト基盤、window 管理の全面自作 | 既存基盤の測定済みの障害が上流でも解決できない。埋め込みの子 window は、winit の測定済みの制約のため自作した（設計の埋め込みの章） |
| N-04 | 要求のない部品、マーケットプレイス、ビジュアルデザイナーの先行開発 | 3 章の規則を満たす実アプリの要求 |
| N-05 | 任意の Rust コード・型変更の完全な Hot Reload | 安全な状態移行とツールチェーン追従の実証 |
| N-06 | 内部実装の完全公開と万能プラグイン API | 複数の実装が、狭い拡張口では足りないことを示す |
| N-07 | 汎用テスト実行器やレコード・再生の自作 | 既存ツールと `kivact::test` で解けない障害 |
| N-08 | 根拠のない 1.0、LTS、非公開 SDK の代理保守 | 対応表、移行計画、設計協力先、保守主体 |

## 8. 優先度と対応 OS

- **P0:** 正しさ、IME、フォーカス、ライフサイクル、宣言済みの OS 品質、重大な回帰。後から API を壊すことになる振る舞いの層、テキスト編集の拡張口の形、フレームクロック、バックエンド型の非漏洩を含む。
- **P1:** アプリを完成させる部品、文書、非同期処理、診断、配布。中核の振る舞いの層と標準部品、アクセシビリティの既定値、部品の文言と地域書式の差し替え、レイアウト崩れの検査、`kivact::test` の E2E、Canvas と画像の書き出し、基本的なアニメーションを含む。
- **P2:** 測定で必要と分かった性能改善、反復時間、高度な描画とアニメーション、実験段階の接続層 SPI。
- **P3:** 新しい OS や独自プラットフォームの正式対応、新しいレンダラー、高度な再読込み。モバイルと移植の設計境界は P3 へ先送りしない。

P0 の欠陥を新しい部品やデモで埋め合わせない。

対応状況は「設計対象」「実験的に動作」「正式対応」の三段階で示す。デスクトップの主対象は Windows と Linux（Wayland・X11、ディストリビューション、IME 環境を固定して確認する）。macOS は実機と保守者がそろったときに対応表へ載せ、それまで macOS 向けの分岐を入れない。Android・iOS は設計と実機検証の対象とし、正式対応とは分ける。埋め込みは Windows と Linux X11 で「実験的に動作」とし、正式対応には主要な DAW（REAPER、Bitwig Studio、Ableton Live、Cubase など）と両 OS の G-03（IME、accessibility）の実機確認を求める。macOS（NSView）の埋め込みは設計対象とし、実機と保守者がそろったときに実装する（完成条件は設計の埋め込みの章にある backend の契約と、共通の契約試験の通過）。

## 9. 指標と見直しの条件

最重要の指標は、対象チームが実用画面を配布し、次のリリースでも維持できることである。

| 指標 | 測定 |
|---|---|
| 導入 | テンプレートから最初の実用画面（一覧、詳細、非同期処理、エラー）までの時間と詰まり。React・SolidJS・Rust の経験別に記録する |
| 実アプリ | dogfooding と外部アプリで、公開 API では実現できなかった操作の数と、アプリ側の回避コードの量 |
| 診断 | 依存の誤り、不要なレイアウト、解放漏れ、レイアウト崩れの原因を特定するまでの時間 |
| 実行時品質 | 入力から表示までの遅延、フレーム時間、CPU・GPU、メモリ、起動時間。待機時と連続更新時を分ける |
| 継続性 | リリース更新時の移行量、外部コンポーネントの追従、実アプリの継続利用 |

次を観察したら、機能追加より本書の改訂を優先する。

- API は好まれても、部品や OS 機能の不足で配布できない → 振る舞いの層、標準部品、OS サービスへ配分する。
- 既存基盤への部品・診断ツールの追加で同じ利益が出る → 既存基盤上の製品へ縮小する。
- スタイルやアニメーションで部品が複雑になり、入力・アクセシビリティ・性能が悪化する → property と効果を減らし、振る舞いの層とテーマを設計し直す。
- 第二の接続層の移植に中核のフォークやバックエンド型の公開が要る → 移植可能な中核の責任を見直す。
- 外部の採用が止まり、作者のアプリだけが使う → 新規性を需要の証拠にせず、利用者の課題に戻る。

## 10. 設計レビューの問い

設計レビューは [テンプレート](REVIEW_TEMPLATE.md) に従い、次の問いを「適合・不適合・未検証・非該当」と理由で判定する。未検証を適合に数えない。

1. 誰のどの仕事が改善するか。実アプリの要求はあるか（P-01、3 章）。
2. 層は 4 章の所有範囲に合っているか。アプリが公開 API だけで作れるものを中核に入れていないか、逆に作れないものをアプリに残していないか。
3. React・SolidJS 開発者に少ない概念で説明できるか。同じことに二つの経路がないか（P-02、3 章の 4）。
4. G-01〜G-07 を満たすか。
5. ライフサイクル、入力、フォーカス、アクセシビリティ、描画の整合を、E2E で確かめたか。部品の文言と地域ごとの書式を差し替えられるか（P-04、P-08）。
6. 性能と保守の全体の費用は釣り合うか。誰が保守するか（P-05、P-09）。
7. バックエンドの型や desktop 固有の前提を公開契約に入れていないか（P-10）。
8. 非目標を暗黙に広げていないか（7 章）。
