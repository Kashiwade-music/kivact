## 6. 別マシンでの再開手順

### 6.1 リポジトリを用意する

既に clone があればその clone を使う。以下は新規 clone の例で、保存先は移行先の環境に合わせてよい。

```bash
git clone --branch refactor/kashiwade/slim-fast https://github.com/kashiwade-music/kivact.git kivact
cd kivact
git submodule update --init --recursive
git status --short
git rev-parse HEAD
```

まず HEAD を本書の基点と照合する。リモートに後続 commit がある場合はそれを読んで再開点を判断する。本書の patch を新しい HEAD に強制適用しない。Rust は `rust-toolchain.toml` の **1.98.1**、clippy / rustfmt を使用する。`vendor/xtask-core` は submodule なので、worktree を追加した場合もその worktree 内で submodule を初期化する。

### 6.2 計測用 scratch を復元する場合

レビューは通常のブランチから始めてよい。未コミットの計測変更が必要なときだけ、付録の patch を取り出し、**基点から作った別の detached worktree**に適用する。製品ブランチ全体へ適用しない。

リポジトリルートに本書を置き、次の Python を実行すると、付録の完全な patch を `claude-prof-scratch.patch` として取り出せる。生成ファイルは一時的な移送物であり、製品コードとして commit する対象ではない。

```python
from pathlib import Path
import hashlib
import re

document = Path("20261110_1145_CLAUDE_CODE.md").read_text(encoding="utf-8")
match = re.search(
    r"<!-- BEGIN PROFILING PATCH -->\n```diff\n(.*?)\n```\n<!-- END PROFILING PATCH -->",
    document,
    re.S,
)
assert match, "profiling patch not found"
payload = (match.group(1) + "\n").encode("utf-8")
expected = re.search(r"PROFILING_PATCH_SHA256: ([0-9a-f]{64})", document).group(1)
assert hashlib.sha256(payload).hexdigest() == expected
Path("claude-prof-scratch.patch").write_bytes(payload)
```

ルートでのコマンド例（Git Bash / Bash）：

```bash
git worktree add --detach ../kv-prof db8d679b35b6bf20141adf4b637fe10979fd4596
git -C ../kv-prof submodule update --init --recursive
cd ../kv-prof
git apply --check ../kivact/claude-prof-scratch.patch
git apply ../kivact/claude-prof-scratch.patch
git status --short
```

clone のフォルダー名を変えた場合は patch の相対パスも変えること。既存の `../kv-prof` がある場合は空いている別名を使う。patch は **tracked 24 ファイルの変更と未追跡 `prof.rs` 1 ファイル、合計 25 ファイル**を含む。`prof.rs` を省くと他の span 挿入箇所が compile できない。

この scratch の注意点：

- root `Cargo.toml` に `[profile.prof]`（release 継承、lto=false、codegen-units=16、strip="none"、incremental=true）を追加。
- `dev/bench` に `kivact-engine` への直接依存、engine に一時的な `pub mod prof` を追加。
- `prof.rs` には広い lint allow と環境変数参照を含む。製品への正式採用・lint 通過を意図したコードではない。
- `kv_latency` の対象は一時的に `[100, 1000, 3000]` から **`[3000]` のみ**へ変更されている。正式 run.sh が要求する 17 場面を満たさず、このまま正式 KPI に使えない。
- `PROF_MANUAL=1` を付けると明示的 `dump()` ごとの集計。未指定だと約 3 秒ごとに集計され、測定区間が混在する。span は入れ子なので時間を単純合算しない。

診断の再現例。`CARGO_TARGET_DIR` は各マシンの空き領域に置き、正式 release 計測用 target と分ける。

```bash
export CARGO_TARGET_DIR="$(cd .. && pwd)/kv-prof-target"
cargo build --profile prof -p kivact-bench --bin kv_stress
cargo build --profile prof -p kivact-bench --features latency --bin kv_latency
# Windows は .exe。Linux では .exe を外す。
ROWS=3000 MODE=row dev/tools/window-lock.sh --timeout 300 -- timeout 11 "$CARGO_TARGET_DIR/prof/kv_stress.exe"
PROF_MANUAL=1 KIVACT_TEST_MIRROR=off dev/tools/window-lock.sh --timeout 600 -- "$CARGO_TARGET_DIR/prof/kv_latency.exe"
```

stress は終了用の timeout で 124 になることがある。診断コマンドの終了条件と試験失敗は区別する。元マシンの試行には lock を通さない latency 実行もあったが、再開時は実 window を開くコマンドを共有 lock 経由に統一する。

### 6.3 別マシンでの正式 KPI の扱い
